## Install on Ubuntu

```sh
sudo apt install ./notchy_0.2.0_amd64.deb
```

The deterministic artifact is produced by `pnpm release:dogfood` into `artifacts/0.2.0/`:
`notchy_0.2.0_amd64.deb` plus a `sha256sum -c`-compatible `notchy_0.2.0_amd64.deb.sha256`.

## Schema status

- Current schema: **6**
- Released source schemas that upgrade in place: **3**, **4**, and **5** (older databases are rejected, never silently touched).
- **Source app 0.1.4 / schema 5 -> target app 0.2.0 / schema 6**: this is a real schema 5 -> 6 migration.

## What changed from 0.1.4

### Native Rust database boundary
- All database operations now route through Rust (`rusqlite`), not the JavaScript `@tauri-apps/plugin-sql` package.
- The npm package `@tauri-apps/plugin-sql` has been removed from `package.json`.
- Browser-side code (`src/lib/db/browser/service.ts`) retains a local `PluginDatabase` interface for E2E test compatibility; the dynamic import path is dead code in production.

### New migration 006
- Schema 6 adds operation-id deduplication for retry-safe writes.
- Protected startup path runs migration 006 after the verified pre-upgrade backup.

### Release gate
- `pnpm release:dogfood` now runs the full automated release verification suite before building the `.deb`:
  - `check:native-db-cutover`, `check:db-contracts`, `cargo test`, `pnpm check`, `pnpm test`, `pnpm test:e2e`, `pnpm test:mutation:db`, `pnpm build`, `cargo check`, `git diff --check`
- `assertClean()` enforces a clean working tree at release start: no tracked modifications, and only explicitly allowed untracked prefixes.

### Crash recovery
- Verified pre-upgrade backup before every migration.
- Atomic file replacement via `fs2` file locking.
- Recovery UI with Retry, Restore, Open backup folder, Copy technical report, Quit.

## Upgrade behavior

- Startup runs the protected sequence: integrity check -> schema inspection -> mandatory pre-upgrade backup (when migration required) -> migration -> post-migration verification.
- Pre-upgrade backups are written to `backups/upgrades/` below the app-data directory.
- **Automatic updates are unsupported**, and **downgrades are unsupported**. A database created by a newer app version (newer schema) is refused, not migrated.

## User-visible changes

### Database recovery screen
If the database cannot be opened safely, the app shows a full-screen recovery screen with app version, latest/detected schema, live database path, and pre-upgrade backup path. Actions: Retry, Restore from pre-upgrade backup (with confirmation), Open backup folder, Copy technical report, Quit.

### Settings -> Backup
- Backup health card: app version, schema version, database path, last routine backup timestamp, last upgrade backup path, last upgrade source schema, and any warning.
- Manual "Create backup now" routine backup.
- Restore a compatible older database from a `.sqlite` file.

### Blocker 1 — Settings → Backup & Data is non-functional under Tauri

`src/routes/settings/backup/+page.svelte:15` reads the database through a raw escape hatch:

```ts
function getRawDb(db: AppDatabase): DatabaseService {
    return (db as unknown as { raw: DatabaseService }).raw;
}
```

`raw` is defined only on the browser client (`src/lib/db/browser/client.ts:421`). The native
client (`src/lib/db/native/client.ts:473`) implements `AppDatabase` without one — deliberately
so (`src/lib/db/client.ts:4`: *"Exposes domain services only: no `execute`, no `transaction`, no
raw SQL"*). Under Tauri `getRawDb()` therefore returns `undefined`, and every call site throws:
`loadHealth` (line 37), `createBackupNow` (56), Export SQLite (83, `VACUUM INTO`), Export CSV (98).

Observed: the Database health card renders only its two buttons and
`Something went wrong. Please try again` — no app version, schema, path, or backup rows — and
`app_meta.last_backup_at` is still `2026-08-19T14:49:47.075Z`, i.e. routine backup has not run
since before the upgrade. The page's own copy (*"Backups are created automatically on every
launch"*) is not true of the native path, which only publishes a backup when a migration needs
one.

The native cutover removed raw SQL from the frontend and never ported this page; the E2E suite
(`src/tests/e2e/backup-restore.spec.ts`) drives the web build on the browser client, where `raw`
does exist, so it stayed green.

Evidence: `artifacts/0.2.0/evidence/backup-page-error.png`.

### Blocker 2 — the pre-upgrade backup is published into `backups/`, not `backups/upgrades/`

The native path published the rollback backup into the backup directory root, while the rest of
the app points at the `upgrades/` subdirectory: `src/lib/db/index.ts:62` computes
`upgradeBackupDir = ${dataDir}/backups/upgrades`, the Settings "Open backup folder" action opens
that path, and this document (`Upgrade behavior`, above) promises `backups/upgrades/`. The
database's own record agrees with the defect:

```
last_upgrade_backup_path = /tmp/step7c/data/com.notchy.app/backups/notchy-backup-v5-0.1.4-01M3CGSB1ASS5VDMKWMHXE4HVJ.sqlite
```

After the migration, `backups/upgrades/` did not exist at all, so the user cannot find their
rollback backup through the UI that is supposed to point at it.

### Post-0.2.0 fixes (committed on `fix/native-backup-upgrades-dir`, `1ecb590`; not in this artifact)

Three defects found while verifying this package are fixed test-first on
`fix/native-backup-upgrades-dir` (`1ecb590`, *fix(backup): publish pre-upgrade backups into
upgrades/ and sweep temp sidecars*):

- **D1 — upgrades directory.** `backup::UPGRADES_DIR` and `DatabaseManager::upgrade_backup_dir()`
  added; the `Older` startup branch publishes into `backups/upgrades/`, and
  `discover_verified_backups` scans both directories so upgrade backups stay visible to
  restore-point discovery. (`retention_deletions` is still exported-but-unwired — it has no
  production caller yet, so retention is not actually enforced on either directory.) Covers
  blocker 2.
- **D2 — restart sweep.** `cleanup_interrupted_publications` now runs at the top of
  `perform_startup` for every startup, not only on the migration branch, so a daily-use launch
  actually collects artifacts a killed publication left behind. Covers the restart case above.
- **D3 — publication sidecars.** `copy_online` opens its destination with the live connection
  policy, which forces WAL, so the temp file acquires `-journal`/`-wal`/`-shm` companions that the
  atomic rename does not move — and the final name carries a *fresh* ULID, so they can never be
  re-associated with the backup they came from. `remove_temp_sidecars` now runs on both the
  success and the error path of `publish_backup`.

Blocker 1 is **not** fixed here; porting `settings/backup` off `db.raw` was next-release work at
the time of `1ecb590`.
