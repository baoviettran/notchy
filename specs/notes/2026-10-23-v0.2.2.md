# Notchy 0.2.2

**Serves:** STORY-009, STORY-013, STORY-015, STORY-023

## Changes

- Independent financial profiles: create, rename, switch, reset and delete with
  session isolation. Existing single-database installations adopt into one profile.
- Backups restore into a new profile; existing profiles remain intact. Shared
  appearance/language preferences stay separate from profile financial settings.
- Profile changes coordinate drafts across the main and Quick Add windows.
- Durable financial retry IDs are scoped to profile identity and survive session
  generation changes, while stale sessions cannot write into another profile.

- Scheduled transactions now post and advance in a single native transaction.
  A failure rolls back the entire per-schedule pass. Catch-up remains capped at
  24 posted occurrences; resume continues from the committed next date.
- Native mutations receive client-owned operation IDs. Pending automatic intents
  survive reload without storing transaction payloads in localStorage. Concurrent
  completions clear only their own intent keys.
- Duplicate, learned-rule upsert, budget copy and reconciliation replay their
  original results. Receipt request hashes include operation targets and notes.
  State-dependent validation happens after receipt replay, inside transactions.
- Release E2E failures are fatal. Tag builds depend on quality checks of the
  same source revision and use a valid coverage comparison base for new tags.
- Settings displays version 0.2.2 in English and Vietnamese.

## Data and upgrade policy

Schema remains **7**. Existing databases are preserved; supported older schemas
use the existing verified upgrade-backup path. Make a manual SQLite backup before
upgrading. Automatic routine backup and retention are not introduced in this patch.
Use SQLite export and restore into a new profile for full recovery; archival table CSVs are not a full
lossless restore format.

A new version prevents future interrupted schedule passes from duplicating
occurrences. It does not infer or delete duplicates already created by older
versions: review suspicious prior scheduled transactions before removing them.

Avoid editing one database concurrently with old and new application binaries.
Receipts created by the new retry protocol belong to the new application version;
use a verified pre-upgrade backup if an older version must be restored.
