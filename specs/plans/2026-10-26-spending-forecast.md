> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Serves:** STORY-040

**Review revision:** 2026-10-26; see [review resolutions](../notes/2026-10-26-plan-review-resolution.md).

**Goal:** Explain available cash and predicted remaining money until the nearest eligible fixed income, using weekly spending medians and a separate draft scenario.

**Architecture:** Native profile SQLite owns expected income, obligations, reserve allocations and coverage settings. Rust evaluates one consistent financial snapshot; browser repositories and pure TS evaluators implement the same fixture-tested domain contract. Posted cash, commitments and statistical predictions remain distinct, and unreceived income never funds current availability.

**Tech Stack:** Rust/rusqlite/Tauri v2; TypeScript/Svelte 5; exact integer/rational arithmetic; Vitest/Playwright.

**Spec:** `specs/2026-10-26-personal-finance-confidence-design.md`, sections 1–3, 6–11.

## Global Constraints

- Execute after automatic-backup and durable-draft plans; preserve their session, revision and atomic-submit contracts. Use Node 22.22.3 and pnpm 10.11.0.
- Add native schema 10/browser schema 9 (`009_spending_forecast.ts`), subject to checking upstream state. Never edit released migrations or assume native/browser versions match.
- Horizon is the nearest unreceived occurrence among active enrolled sources funding selected spending accounts. Day 10 is configuration, not code. Due-today/overdue or no eligible source pauses dated A/P.
- Selected cash/checking accounts by default; savings opt-in; credit limits, receivables and unreceived income are not cash.
- `A = B - C - R - E`. `P = A - sum(max(V_b - R_b - C_b, 0))`; keep negative shortfalls. Do not subtract envelope allocations/goal targets automatically.
- Use twelve complete Monday–Sunday weeks before the current week, minimum eight confirmed-covered weeks. Missing coverage is not zero; covered zero weeks count. No ML, seasonality or fabricated confidence intervals.
- Preserve exact monetary arithmetic. Native i128/browser BigInt intermediates; all IPC amounts are checked safe integer minor units. Round up once after summing rational bucket contributions.
- Both locales, flat keys, Svelte runes, existing primitives and locale boundary rules. Never write generated Paraglide files.
- Red → green → verify → commit. `pnpm test` before every commit; `pnpm check` for TS/Svelte; affected Rust suites for native. No broad staging, personal CSV access or changes to `docs/`.

- Verification must report a nonzero executed-test count and include the newly named behavior. A compile error is a valid initial red state; a successful command selecting zero tests is never green. Run each named integration test target without an unverified substring filter; inspect test discovery/counts before accepting results.

## Review Focus

1. A receipt is overdue, due today, or goes straight to excluded savings: never advance the horizon as if spendable cash arrived — Task 2.
2. A payment/edit/delete/refund changes a linked bill or reserve: update both cash and protection in one transaction — Task 3.
3. Rotating categories each have zero medians despite steady aggregate spending: forecast the aggregate weekly median, attribute shares with a conserved total, and recompute category explanations consistently — Task 6.
4. A half-unit aggregate median, fractional category shares or large balances overflow/round differently between adapters: checked exact arithmetic and one final rounding — Tasks 5–6.
5. A pending draft submit already committed or an edit has a changed baseline: resolve receipts/conflicts before scenario evaluation; never subtract the draft again — Task 7.

Use existing scalar types (`ScheduleFrequency`, `NewTransaction`) rather than new spelling variants. Strings in DTO tables denote text IDs/dates; money/revisions are checked integers, enabled/fundsSpending are booleans, list fields are arrays. `ForecastResult` also contains `medianWeeklyTwice: string | null` for the aggregate baseline and `baselineInterval: number | null`. `bucketBreakdown` contains `{ bucketId: string | null; historicalWeight: string; intervalNumerator: string; denominator: string; reserveOffset: number; obligationOffset: number; additional: number }[]`; exact rational numerators are decimal strings in IPC, and per-bucket display rounding must not be summed to compute P.

`ForecastMutation` is `{ expectedRevision: number }` intersected with a discriminated union (`kind`, payload) with: `save-settings` (ForecastSettings), `save-source` (IncomeSource), `enroll-schedule` ({scheduleId, fundsSpending}), `resolve-income` (IncomeResolution), `save-obligation` (ForecastObligation), `settle-obligation` ({obligationId, transactionId: string or null, transaction: NewTransaction or null, amount}), `cancel-obligation` ({id}), `save-reserve` (ForecastReserve), `allocate-reserve` (direct transaction/reserve/amount; earmarkId is native-owned), `set-bill-earmark` (SaveBillEarmarkInput), `release-bill-earmark` ({id}), `save-coverage` ({ranges: ForecastCoverage[]}), `set-exceptional` ({transactionId, exceptional: boolean}). Save-source handles enable/disable; IDs of new records are client ULIDs. Request-only DTOs omit derived balances/status/result IDs; require `expectedRevision` against ForecastState.contentRevision on write, checked after receipt replay. New-input/patch types are named `SaveSourceInput`, `SaveObligationInput`, `SaveReserveInput`, `SaveBillEarmarkInput = { id: string; reserveId: string; obligationId: string; amount: number }` and select writable DTO fields explicitly, not arbitrary Partial objects.

`ForecastMutationResult = { entityId: string | null; transactionId: string | null; contentRevision: number }`.

`AppDatabase.forecast` exposes `read(): Promise<ForecastState>`, `mutate(input: ForecastMutation, options?: MutationOptions): Promise<ForecastMutationResult>`, `evaluate(includeDrafts: boolean): Promise<ForecastEvaluation>`. Native commands are `forecast_read`, `forecast_mutate`, `forecast_evaluate`. Mutation is receipt-backed with a stable request; native derives today, ownership and paths. Pure evaluators receive injected `asOf` in tests.
